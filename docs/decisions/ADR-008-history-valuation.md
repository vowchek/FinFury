# ADR-008: История стоимости портфеля (графики фазы 2)

- **Статус:** ✅ Accepted
- **Дата:** 2026-09-10
- **Контекст задачи:** фаза 2, подзадача 2.4 «Графики стоимости и доходности»

## Контекст и проблема

Истории стоимости портфеля в системе нет. `PriceService` (ADR-005) отдаёт **текущую** цену (in-memory кэш TTL 15 мин + previousClose на день; провайдеры MOEX/Yahoo/CoinGecko), таблиц истории цен в БД нет. График «стоимость портфеля во времени» нельзя посчитать корректно в прошлое без исторических цен.

## Рассмотренные варианты

1. **Периодические valuation-снапшоты** — новая таблица `portfolio_snapshots`, запись стоимости по текущим ценам (эндпоинт/фоновая задача). Плюс: просто, точная фиксация «на момент». Минусы: история накапливается только с момента внедрения (график пуст до накопления), нужен триггер записи (фоновые задачи — фаза 3), для MVP с Stub-ценами снапшоты фиксируют плоскую стоимость.
2. **Хранение исторических цен** (`asset_prices`: symbol, date, close) + расчёт стоимости назад по транзакциям. Плюс: правильная рыночная история. Минусы: **нет источника исторических цен** (фаза 3, интеграции) — таблица будет пустой, расчёт невозможен.
3. **Гибрид**: снапшоты вперёд + расчёт назад по транзакциям с последней известной ценой (с пометкой точности).

## Решение

Вариант 3, с упрощением MVP-фазы 2: **расчёт истории на лету от транзакций** (единая книга, ADR-003), без таблицы снапшотов в фазе 2.

- Стоимость на дату `D` = денежный остаток на `D` + Σ (количество актива на `D` × цена на `D`).
- Количества и себестоимость на `D` берутся из чистых функций `calculateCashBalance` и `calculateAverageCostBasis` (AVCO) на срезе транзакций `date ≤ D` — переиспользуется логика позиций/кэша, без новой производной сущности.
- Цена на `D`: пока исторических цен нет — **текущая** цена из `PriceService`, точка помечается `priceSource: 'current'`. Если цены нет вовсе — себестоимость (AVCO), `priceSource: 'cost'` (плоский участок кривой). Когда в фазе 3 появится источник исторических цен (`asset_prices`), резолвер заменяется на цену на дату — та же схема расчёта начнёт давать рыночную историю без изменения контракта.
- Доходность по периодам — **Modified Dietz** по календарным месяцам: `pnl = Δvalue − netFlow`, `returnPct = pnl / (valueStart + Σ flow × вес)` (вес — доля периода, оставшаяся после движения денег). Учитывает вводы/выводы, согласовано с правилами кэша.
- Снапшоты (`portfolio_snapshots`) откладываются в фазу 3 вместе с фоновыми задачами: станут кэшем/источником для длинных диапазонов (смягчение O(бакеты × транзакции) на лету).
- Ось времени: UTC, `date` — календарные дни `YYYY-MM-DD`.

## Последствия

- Плюсы: график работает сразу (включая «в прошлое» по движению денег), нулевая миграция схемы, чистая логика → юнит-тесты краевых случаев (opening, sell, DRIP, дробные количества).
- Минусы / ограничения (честно): при Stub-ценах «рыночная» часть кривой плоская — форма графика отражает движение денег, а не рыночные изменения. Это помечено в контракте (`priceSource`) и в UI; исправится автоматически с реальными ценами (фаза 3).
- Изоляция по `userId` — как в остальных модулях (счёт не принадлежит пользователю → 404).
- Деньги — целые минимальные единицы (ADR-002); MVP — одна валюта на диапазон (валюта счёта/первого счёта), мультивалютный пересчёт — фаза 4.
