# ADR-003: Единая транзакционная книга (snapshot → opening-транзакция)

**Status:** Proposed
**Date:** 2026-09-09
**Deciders:** Владелец проекта

## Context

Приложение поддерживает два ручных сценария ввода (см. data-entry-modes.md):
- **A. Существующий портфель** — пользователь вводит текущие позиции и cost basis, не воспроизводя историю.
- **B. Новый/небольшой портфель** — полный учёт транзакций.

Вопрос: как хранить позиции, чтобы оба сценария работали без двух параллельных моделей данных?

## Decision

Ввести **единую транзакционную книгу**: все позиции и стоимость выводятся из транзакций. Snapshot-ввод (сценарий A) **конвертируется в `opening`-транзакцию** (покупка на дату начала ведения по указанному cost basis). Параллельная «позиционная» модель не вводится.

## Options Considered

### Option A: Единая книга + opening-транзакция — выбрано
| Dimension | Assessment |
|---|---|
| Complexity | Medium |
| Cost | Низкий |
| Scalability | Достаточно |
| Team familiarity | Средняя |

**Pros:** одна модель данных; позиции всегда консистентны с транзакциями; сценарий A — просто «быстрый старт» книги; легко доимпортировать историю позже.
**Cons:** нужно аккуратно обрабатывать `opening`-транзакции (не пересчитывать как обычные покупки); cost basis для сценария A — средний (AVCO).

### Option B: Отдельная таблица позиций как источник истины
| Dimension | Assessment |
|---|---|
| Complexity | Low |
| Cost | Низкий |
| Scalability | Достаточно |
| Team familiarity | Высокая |

**Pros:** просто; позиции хранятся напрямую.
**Cons:** две модели (позиции + транзакции) расходятся; сложно поддерживать cost basis и реализованную прибыль; сценарий B требует синхронизации.

### Option C: Только транзакции, без snapshot-режима
| Dimension | Assessment |
|---|---|
| Complexity | Low |
| Cost | Низкий |
| Scalability | Достаточно |
| Team familiarity | Высокая |

**Pros:** максимально просто.
**Cons:** не покрывает сценарий A (существующий портфель) — ключевое требование продукта.

## Trade-off Analysis

Сценарий A — важное продуктовое требование («у меня уже есть портфель»). Вариант B создаёт риск рассинхронизации двух моделей. Вариант C не покрывает требование. Вариант A покрывает оба сценария одной моделью: snapshot-ввод порождает `opening`-транзакцию, и дальше всё работает единообразно.

## Consequences

- Позиции — производная (кэш/агрегация) от транзакций, не источник истины.
- `opening`-транзакции помечаются флагом и не участвуют в расчёте реализованной прибыли как обычные сделки.
- Cost basis для сценария A — средний (AVCO); для сценария B — по партиям (FIFO/AVCO).
- Возможен «апгрейд» сценария A → B доимпортом истории (авто-режим).
